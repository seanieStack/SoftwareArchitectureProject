# Architecture Overview

The system is built as microservices because thats what the brief asks for. There are two main domain services and a few supporting ones.

## The bits

- **api-gateway** - the only thing the browser talks to. Checks JWTs and routes things to the right service.
- **core-service** - books, users, auth. Owns the catalogue and issues JWTs.
- **support-service** - borrows, fines, notifications. Does the lifecycle stuff.
- **eureka-server** - service discovery so the gateway can find services by name.
- **config-service** - shared config.
- **RabbitMQ** - for async events (notifcations).
- **Postgres** - one db per domain service so they cant peek at each others tables.

## Picture

```
Browser
   |
   v
[ React SPA ]  --HTTPS-->  [ API Gateway ]  --lb://-->  core-service ---> core-db
                                                       \
                                                        --> support-service ---> support-db
                                                                  |
                                                                  +--> RabbitMQ --> NotificationListener
```

The gateway sticks `X-User-Id` and `X-User-Role` headers on the request after it verifies the JWT, so the downstream services dont have to parse the token again.

## Why split into two services

`core-service` owns the catalogue and users. `support-service` deals with the lifecycle (borrows, fines, notifs). They cant share a db. When support needs to know if a book exists it calls a `/api/internal/...` endpoint on core.

This means they can be deployed, tested and scaled seperately which is the whole point of microservices.

## What we didnt do

- No distributed tracing (out of scope)
- No saga/2PC, the borrow flow is best effort
- No outbox pattern for events
- Schema is auto-generated by JPA (`ddl-auto: update`) instead of using flyway/liquibase

These are fine for a uni project but you wouldnt do it like that in real life.
